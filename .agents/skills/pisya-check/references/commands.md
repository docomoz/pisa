# Существующие проверки и подготовка сборки

Команды выполняются из корня проверяемого снимка. Назначение и побочные эффекты
перепроверь в исходниках при изменении скриптов. Сохраняй полный вывод и код
завершения; `tee` без `pipefail` скрывает ошибки. Ни одна команда ниже сама
по себе не выполняет весь `$pisya-check` и не заменяет визуальную проверку.

## Снимок и автоматические проверки

После нового функционала или фикса запускай единый обязательный набор:

```sh
python3 scripts/pretest.py
```

Он сохраняет `summary.json`, `report.md` и отдельный лог каждой команды в
`build/pretest/`. Полный прогон включает core, дизайн-систему, сайт, versioning,
проверки самого runner и нативные probes меню, клавиатуры, аудиоокна и общих
контролов. Ошибка, timeout, изменение снимка или недоступная обязательная
проверка дают ненулевой код. Отдельные команды ниже нужны для диагностики,
а не для повторения уже успешного неизменившегося прогона.
`--portable` пригоден для Linux и явно оставляет macOS-часть непроверенной.
Границы новой автоматики и исторические причины: `docs/pretest.md`.

```sh
git rev-parse HEAD
git branch --show-current
git status --short
git diff --check
git submodule status --recursive
python3 scripts/check-design-system.py
swift test
bash Tests/Native/run-quit-shortcut-test.sh
bash Tests/Native/run-capture-window-test.sh
```

`swift test` — полный набор ядра, не фиксированное историческое число тестов.
Сохрани также хеши staged/unstaged diff, содержимого новых файлов и dirty-файлов
подмодулей, вошедших в сборку. Один HEAD не описывает грязное рабочее дерево.
Для независимых запусков Swift используй отдельный `--scratch-path` внутри
каталога прогона. Не запускай второй SwiftPM в занятой `.build`.

Сайт: `npm test --prefix website`. Это собирает Worker в `website/dist/server`
и выполняет локальные тесты скачивания, статики и аналитики. Развёртывание
и реальная доставка событий этим не проверяются. Сайт с выбранного снимка
просмотри отдельно на компьютере и узком мобильном экране.

## Одна окончательная нативная сборка

`./scripts/build.sh` — существующий полный путь Pretest + Release + упаковка + DMG.
Он изменяет проект через XcodeGen, подготавливает/патчит Vendor, копирует
`dependencies.resolved.json`, может устанавливать runtime. Поэтому его нельзя
без проверки запускать поверх параллельной незавершённой работы.

Подготовь отдельный каталог исходников для сборки. Выбери и запиши один вариант:
коммит либо снимок текущего дерева с явно включёнными dirty-файлами и подмодулями.
`git archive HEAD` сам по себе не содержит dirty-файлы, новые файлы и содержимое
подмодулей. Не выдавай такую сборку за проверку всех текущих изменений.
При копировании не переноси приватные ключи и `.signing.env`; необходимые
бинарные зависимости и модели проверяй по фактическим локальным путям.

Сборку выполняет один владелец. Сохрани версии SDK/зависимостей и весь build log.
Изменение Vendor сборочным скриптом включи в происхождение результата.
Отсутствие возможности получить воспроизводимый снимок — `BLOCKED` для сборки,
а не основание чистить, stash/reset или коммитить чужую работу.

Для полученной `.app` задай абсолютный путь `audit_app`, затем проверь:

```sh
codesign --verify --deep --strict "$audit_app"
plutil -extract CFBundleShortVersionString raw "$audit_app/Contents/Info.plist"
plutil -extract CFBundleVersion raw "$audit_app/Contents/Info.plist"
shasum -a 256 "$audit_app/Contents/MacOS/Pisya"
codesign -d --entitlements :- "$audit_app"
```

Проверь также главный файл, `Contents/Helpers/pisya-mcp`, вложенные dylib,
Metal-ресурсы, модели/словари и лицензии. Утверждение о подписи делай по
реальному результату, не по историческому наличию Developer ID/notarization.
Упакованный MCP-помощник должен соответствовать проверенной сборке.

## Изолированные native self-tests

Запускай только после сверки существующих обработчиков в `Launcher.swift`.
Следующие входы используют временные тестовые данные в исследованной версии:

```sh
"$audit_app/Contents/MacOS/Pisya" --library-self-test
"$audit_app/Contents/MacOS/Pisya" --model-setup-self-test
"$audit_app/Contents/MacOS/Pisya" --voice-profiles-self-test
"$audit_app/Contents/MacOS/Pisya" --queue-self-test
"$audit_app/Contents/MacOS/Pisya" --source-link-self-test
"$audit_app/Contents/MacOS/Pisya" --term-review-self-test
```

`--source-link-self-test` может инициировать воспроизведение синтетического аудио:
он относится владельцу UI/звука. `--meeting-title-self-test` использует модель
названий, возможна загрузка; отдельно проверь его prerequisites и отмену.
Новый `--dictionary-self-test` включай только если он существует в окончательном
снимке: управление словарём вошло в параллельный коммит `44c2444` во время создания процедуры.

Не используй `--self-test` как универсальный безопасный smoke: текущий обработчик
пишет `smoke-result.json` в обычную Application Support. Другие diagnostics
сначала изучи: часть требует конкретных входных файлов и моделей.

## Интерфейс

```sh
"$audit_app/Contents/MacOS/Pisya" --interface-preview
"$audit_app/Contents/MacOS/Pisya" --interface-preview --medium-text-preview
"$audit_app/Contents/MacOS/Pisya" --interface-preview --large-text-preview
"$audit_app/Contents/MacOS/Pisya" --term-review-preview
"$audit_app/Contents/MacOS/Pisya" --term-review-preview --large-text
"$audit_app/Contents/MacOS/Pisya" --voices-preview
"$audit_app/Contents/MacOS/Pisya" --setup-preview
```

Запуски последовательные, предыдущую тестовую копию закрой по её PID/окну.
Не используй `killall Pisya`. Главный preview имеет временную библиотеку,
меню состояний и размеры 1200 × 800 и 980 × 660. Размеры текста 100%, 110%,
120% проверяются отдельно; недоступные состояния добавь как блокеры.

Для Finder-запуска preview документирован ключ `PisyaInterfacePreview` только
в тестовой копии. Изменение Info.plist/идентификатора требует новой подписи;
такая копия не доказывает неизменённую подпись и TCC-поведение релизного пакета.
Сохрани сравнение основного кода/ресурсов до и после подготовки копии.

Preview показывает настоящие компоненты, но имеет свои меню и фиктивное
состояние: ⌘Q, status menu, настоящий импорт/запись, persistence/restart,
настройки обновлений проверяй также обычным запуском изолированной копии.
Обычный запуск с тем же bundle ID без доказанной изоляции может открыть
пользовательскую библиотеку. Не делай этого ради формальной галочки.

`bash Tests/Native/run-status-menu-test.sh` открывает меню AppKit. Только
владелец UI может запускать этот probe; он не заменяет мышь в итоговой `.app`.
`QuitShortcutProbe` проверяет маршрутизацию событий, а не все настоящие sheets.

## Распознавание и устройства

```sh
bash Tests/Native/run-vocabulary-test.sh "$audit_app/Contents/MacOS/Pisya"
python3 Tests/Native/run-recognition-quality-test.py --app "$audit_app/Contents/MacOS/Pisya" --output "$audit_run/recognition.jsonl"
```

Задай абсолютный `audit_run`, создай его до команды. Нужны установленные модели
и голоса macOS Milena/Samantha. Этот корпус синтетический, обе дорожки,
по умолчанию `pipeline`; выводи действительные WER и ошибки каждого примера.
Скрипт WER нормализует регистр, пунктуацию и е/ё: орфографию проверяй отдельно.
`--modes` передавай только поддерживаемые текущим `RecognitionQualityTests`.
Собственный `--corpus` с эталонами остаётся локальным; эталонные фразы не
передаются распознавателю как подсказки.

`--echo-regression-test`, `--live-pipeline-test`, `--speech-pipeline-test`,
`--audio-pipeline-test` — расширенные проверки: сначала прочитай их входы,
ресурсную стоимость и побочные эффекты. Фиксируй near/remote, эхо/тишину/перекрытия,
громкость и временные границы. Replay не заменяет полный производственный путь.

`--capture-self-test` действительно включает микрофон/системное аудио и проигрывает
тон. Не запускай его во время пользовательского звонка без согласованного
сеанса. Он проверяет два коротких цикла захвата, но не смену гарнитуры, сон,
переподключение и автозапись. Эти сценарии остаются отдельными ID.

## Полная встреча через производственный путь: ASR-09

Это отдельный маршрут, а не неизвестный diagnostic flag. До запуска владелец UI
проверяет текущие `MeetingLibrary`, `AppState` и обработчик повторной расшифровки:
где находятся Audio/Meetings/Models, как выбирается root и передаются offsets.
Если безопасная изоляция обычного приложения не доказана — ASR-09 BLOCKED.
Нельзя заменять этот пункт запуском preview или context replay.

1. Выбери заранее ограниченную встречу из согласованного локального корпуса.
   Скопируй её JSON, все исходные дорожки и смещения в отдельную тестовую
   библиотеку, сохрани идентификаторы/таймкоды. Запиши SHA-256 исходников и копий.
   Источники остаются read-only. Модели и их изменяемый кэш принадлежат тестовой
   среде; не перенаправляй запись кэша в пользовательские файлы.
2. Подготовь обычную копию окончательного приложения с доказанно отдельным
   контейнером. Изменение bundle ID/подписи задокументируй, как для UI-копии выше.
   Проверь путь открытых файлов и отсутствие обращения к production library.
   Пройди короткий synthetic smoke этой изоляции до копирования частного корпуса.
3. В обычном интерфейсе выбери скопированную встречу и команду «Расшифровать
   заново». Обе дорожки и offsets должны попасть в тот же производственный путь,
   что использует приложение; отдельный импорт каждой дорожки не эквивалентен.
   Для синтетического однодорожечного end-to-end можно использовать обычный
   «Импортировать аудио…», но это более узкое доказательство.
4. Дождись ready либо конкретной ошибки в пределах заданного времени. Сохрани
   JSON результата, лог, экспорт и состояния UI. Не исправляй распознанный текст
   вручную до оценки. По локальным эталонам проверь все выбранные контрольные
   места, окончания, границы, хвост, дубли и атрибуцию голосов; неопределённое
   оставь неподтверждённым. Сравни SHA оригиналов и исходных копий после прогона.
5. Укажи полный маршрут, corpus revision, модель, дорожки, границы первого прохода,
   automatic/manual distinction. При timeout не запускай ту же встречу заново
   без диагностической причины и не переходи автоматически ко всей библиотеке.

## MCP, экспорт и выпуск

Контракт и формат ошибок: `docs/mcp.md`, реализация `Sources/PisyaMCP`, тесты
`MCP*Tests`, `TranscriptEvidenceTests`, `TranscriptLinkTests`. Проверь настоящий
упакованный процесс с JSON-RPC handshake, открытым stdin и временной библиотекой,
пять инструментов, отключение доступа в уже открытом клиенте и повреждённые данные.
Фактический способ задания test root найди в текущем сервере; не выдумывай env var.
Проверка клиента и регистрация сервера — разные действия: не меняй конфигурацию
пользовательского клиента ради аудита без необходимости и отдельного поручения.

Экспорт Markdown и `.m4a` проверяй на синтетической встрече: прочитай итоговый файл,
сверь текст/таймкоды/длительность/смещение дорожек, отмену и повторное открытие.
Документ об аналитике — `docs/analytics.md`; локальные тесты схемы не доказывают
доставку события в сервис. Не отправляй синтетические production events ради теста.

Для release проверь DMG через `hdiutil verify`, копию приложения внутри него,
лицензии, относительные связи dylib (`otool -L`), подписанный appcast и SHA-256
артефактов по существующим `docs/releasing.md` и release scripts **если они есть
в проверяемой ветке**. Их отсутствие при наличии функции в установленном продукте
требует разбора расхождения, а не тихого исключения из аудита. Установку,
автообновление и Homebrew испытывай изолированно; публикация не входит в аудит.
