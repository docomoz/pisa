# Проверка Pisya

Запуск: `$pisya-check` (ежедневный), `$pisya-check full` (расширенный),
`$pisya-check release` (перед выпуском). Это ручной аудит, без создания расписания.
Проверяется определённое состояние проекта; успешные тесты не доказывают исправность всего приложения.

## Порядок

1. Найди корень Pisya, прочитай `AGENTS.md` и [матрицу](references/matrix.md).
   Зафиксируй HEAD, ветку, dirty diff, новые файлы, состояние подмодулей,
   текущие процессы и путь/версию установленного приложения.
   Исторические ограничения смотри в [источниках](references/history.md).
2. Выбери обязательные ID по режиму и изменениям. При изменении общего компонента
   включи всех его потребителей. Назначь каждому ID исполнителя, ожидаемый результат
   и доказательство; остальные ID тоже перечисли как `NOT RUN` с причиной.
3. Выполняй аудит мультиагентно по [схеме оркестрации](references/orchestration.md).
   Передавай агентам только назначенные ID, снимок состояния и нужные файлы.
   Один исполнитель владеет интерфейсом; остальные не двигают мышь, не открывают
   окна, не запускают звуковые проверки. Сборку готовит один исполнитель.
4. Выполни `python3 scripts/pretest.py` как обязательную автоматическую часть
   и сохрани её отчёт. Если полный Pretest уже выполнен на том же снимке,
   используй его доказательства без повторного запуска. `--portable` не даёт
   PASS нативной части. Для остальных ID используй существующие
   [команды](references/commands.md). Сборка и тесты
   относятся к одному снимку исходников, зависимостей и ресурсов. Для приложения
   запиши путь, версию, хеш исполняемого файла и результат проверки подписи.
   Финальный UI проверяй именно на этой сборке.
5. Собери [отчёт](references/report.md), проверь доказательства агентов и полноту
   ID. При изменении исходников за время аудита пометь затронутые результаты
   устаревшими и перепроверь только их на новом снимке. Если состояние продолжает
   меняться, закончи с `BLOCKED`, указав проверенный снимок.

## Границы

- По умолчанию аудит не исправляет код, не устанавливает и не публикует приложение.
  Если пользователь отдельно поручил исправления, выполняй их отдельным этапом,
  затем повтори затронутые проверки. Не включай чужие изменения в коммит.
- Текущую запись, обработку и очередь не прерывай. Изолированный UI допустим,
  если подтверждены отдельная библиотека и отсутствие конфликта ресурсов.
  При нагрузке отложи распознавание; выполни остальные независимые проверки.
- Используй синтетическую библиотеку. Оригиналы встреч не перерасшифровывай
  и не изменяй. Проверки микрофона, устройств и настоящего звонка требуют
  согласованного тестового сеанса; без него соответствующие ID — `BLOCKED`.
- Физическую клавиатуру проверяй отдельно от автоматического ввода. Без наблюдения
  либо ответа пользователя этот пункт не получает `PASS`. Тест с подставными
  данными не подтверждает настоящую запись, diarization или приватную интеграцию.
- Не повторяй успешные неизменившиеся проверки. После сбоя допустимы диагностика
  и один осмысленный повтор; дальше зафиксируй причину и результат. Клип, replay
  стадии и полный прогон — разные доказательства.
- Все логи, снимки и приватные данные сохраняй в игнорируемом
  `build/audits/<дата-время>/`. Отчёт связывает каждый ID с доказательством.
  Недоступные инструменты/модели и непройденные проверки называй явно.
