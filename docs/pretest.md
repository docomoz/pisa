# Pretest и регрессии интерфейса

Pretest — автоматическая проверка после каждого нового функционала и фикса.
Запуск из корня проекта:

```sh
python3 scripts/pretest.py
```

`scripts/build.sh` запускает эту команду до подготовки зависимостей, сборки и
упаковки. Workflow `Pretest` запускает её на macOS при push и pull request.
Отчёт CI относится к SHA запуска; зелёный результат старого коммита не относится
к более поздним изменениям. Настройки защиты ветки не изменяются этим workflow.

## Результат и условия запуска

Полный набор требует macOS 15+, Swift/Xcode, Python 3.9+, Node.js 24 и активную
графическую сессию. Он использует временные синтетические данные. Микрофон,
пользовательская библиотека, модели распознавания, ключи подписи и установленная
копия приложения для этого набора не нужны.

У каждой команды отдельный лог. `summary.json` и `report.md` в
`build/pretest/<идентификатор>/` содержат снимок исходников и статусы. `FAIL`
означает воспроизведённую ошибку команды, timeout или изменение исходников за
время проверки. `BLOCKED` означает недоступную обязательную среду/инструмент.
Оба результата возвращают ненулевой exit code и останавливают сборку.

```sh
python3 scripts/pretest.py --list
python3 scripts/pretest.py --portable
python3 scripts/pretest.py --output-dir build/pretest/manual-review
```

`--portable` проверяет только переносимую часть. Его успех не означает, что
пройдены Swift, AppKit, SwiftUI или визуальные сценарии. При полном запуске
отсутствие macOS не превращает обязательные проверки в успешные пропуски.

## Состав

| Набор | Что проверяет | Что остаётся за его пределами |
| --- | --- | --- |

| Versioning | Версии при коммитах, параллельных ветках и слияниях; сохранение незакоммиченных правок | Фактическая доставка обновления пользователю |
| Pretest runner | Передача ошибок/блокировок/timeout, логи, неизменность снимка, ограниченный portable scope | Поведение приложения |

## Почему добавлены эти проверки

Срез: `b3c0382`, 12 ноября 2026. Просмотрены последние 70 записей истории Git
(8–12 ноября, включая merge-коммиты), выбранные исправления и существующие тесты.
Использован прежний [аудит истории](../.agents/skills/pisya-check/references/history.md)
от 8 ноября с указателями исходных сессий. Новые первичные чаты Codex 8–12 ноября
не были доступны в этой среде. Это обновление по исходникам и истории фиксов;
оно не является повторным чтением 50–70 пользовательских чатов. Количество
сессий/форков в прежнем аудите не равно числу независимых чатов.

## Как добавлять следующий фикс

1. Зафиксировать воспроизведение: действие, состояние, данные, масштаб/размер,
   ожидаемый результат. Найти существующий ID в матрице `pisya-check`.
2. Добавить тест к реальной функции или production-контролу. Для визуального
   дефекта проверять отрисовку/геометрию, для состояния — переход и результат.
   Не заменять это поиском имени метода или модификатора в тексте исходника.
3. Подтвердить чувствительность теста: возвращённый дефект или отрицательный
   контроль должен падать. Не утверждать red/green, если старую ревизию не запускали.
4. Исправить причину, выполнить весь Pretest на окончательном снимке. При изменении
   снимка перепроверить затронутый результат. При ошибке сохранить лог, устранить
   причину и повторить соответствующую проверку.
5. После UI-изменения пройти затронутые маршруты окончательного приложения по
   матрице `pisya-check`: окна/масштабы, focus/blur/Tab, открытые/закрытые блоки,
   пустые/длинные данные и конец прокрутки. Для общего компонента — все потребители.
6. В итоговом сообщении указать коммит, фактические проверки и существенное
   непроверенное. Пройденный core suite не подтверждает физическую клавиатуру,
   системные диалоги, реальные устройства или весь UI.
