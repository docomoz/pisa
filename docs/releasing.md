# Выпуск Pisa

DMG для Apple Silicon, подписанный список обновлений Sparkle и контрольная сумма публикуются вместе в GitHub Releases. Homebrew устанавливает тот же DMG через [docomoz/tap](https://github.com/docomoz/homebrew-tap). Встроенное обновление работает для обоих способов установки.

## Подготовка версии

Перед созданием новой рабочей копии найдите готовые сборки целевого коммита и результаты их проверок, в том числе в других рабочих деревьях и недавних задачах. Проверьте происхождение артефакта, версию и номер сборки, снимок исходников, зависимостей и ресурсов и отчёт об успешном полном Pretest. Если всё совпадает и артефакт подходит для выпуска, используйте готовый DMG и существующие результаты без повторной сборки и прогона тестов. Отдельно проверьте то, что необходимо для публикации, включая подпись и подготовку файлов обновления.

Если подходящей сборки или подтверждений нет, подготовьте сборку через `scripts/build.sh` с полным Pretest. При возможности используйте безопасную исходную рабочую копию для повторного использования совместимых результатов компиляции. Не меняйте чужие незавершённые правки; если безопасно использовать существующую копию нельзя, подготовьте отдельную. Простое копирование каталога `build` в другой путь не гарантирует сохранения инкрементального кэша.

1. Проверьте номер версии и сборки в `Resources/Info.plist`: установленный Git-хук увеличивает их при коммите. Sparkle определяет порядок обновлений по `CFBundleVersion`.
2. Напишите заметки к релизу в Markdown. Их увидят в GitHub и в окне обновления Pisa.
3. Используйте проверенный готовый DMG или соберите его при отсутствии подходящего, затем подготовьте файлы для загрузки, подставив новую версию в имя образа.

   ```sh
   # Только если подходящей проверенной сборки ещё нет:
   ./scripts/build.sh
   ./scripts/prepare-release.sh build/Pisa-0.4.4-arm64.dmg /path/to/release-notes.md
   ```

   В `build/release-v0.4.4/` появятся готовый DMG, три подписанных файла `pisa-updates.xml`, `pisa-appcast.xml` и `appcast.xml`, `SHA256SUMS` и описание Homebrew `pisa.rb`. Загружайте эту копию образа. Подпись и контрольная сумма вычислены для её байтов.

Для подписи нужен закрытый ключ Sparkle из локальной связки ключей с именем аккаунта `pisya`. Скрипт сверяет его открытый ключ с ключом внутри DMG. Для резервной копии используйте `generate_keys --account pisya -x /path/to/private-backup` из `build/SourcePackages/artifacts/sparkle/Sparkle/bin/`. Храните копию в защищённом месте. Ключ из резервной копии можно импортировать через `generate_keys --account pisya -f /path/to/private-backup`. Сохранение того же ключа позволяет установленным копиям получать следующие версии.

## Публикация

1. Загрузите коммит в GitHub и создайте черновик релиза. Укажите точный коммит сборки и добавьте пять файлов.

   ```sh
   gh release create v0.4.4 --draft --target COMMIT --title "Pisa 0.4.4" \
     --notes-file /path/to/release-notes.md \
     build/release-v0.4.4/Pisa-0.4.4-arm64.dmg \
     build/release-v0.4.4/pisa-appcast.xml build/release-v0.4.4/appcast.xml \
     build/release-v0.4.4/pisa-updates.xml build/release-v0.4.4/SHA256SUMS
   ```

2. Когда релиз готов, опубликуйте его как обычный релиз и отметьте как **Latest**. По адресу `releases/latest/download/pisa-updates.xml` Pisa получает список обновлений текущего релиза. Предрелизы можно распространять через их собственные страницы.
3. Проверьте загрузку DMG из GitHub и «Проверить обновления…» в предыдущей версии с поддержкой Sparkle.
4. Скопируйте сгенерированный `pisa.rb` в `Casks/` репозитория tap, проверьте `brew audit --cask --strict --online docomoz/tap/pisa` и опубликуйте изменение. Строка `auto_updates true` сообщает Homebrew, что Pisa сама устанавливает новые версии. Для принудительного обновления через Homebrew используйте `brew upgrade --cask --greedy docomoz/tap/pisa`.

## Автоматическая версия коммитов

После клонирования выполните `python3 scripts/versioning/install.py`. Установка действует на все рабочие деревья этой копии Git. При обычном `git commit` хук выбирает следующий patch-номер и номер сборки с учётом локально известных веток, удалённых веток и тегов. Другие неиндексированные изменения файла сохраняются. Перед работой с несколькими копиями обновляйте ссылки через `git fetch --all --tags`: независимые копии без актуальных ссылок могут выбрать одинаковые номера.

Git не позволяет хуку надёжно изменить дерево автоматического merge-коммита. Для слияния выполните `git merge --no-commit <ветка>`, затем `git commit`; если обычный merge уже остановлен хуком, достаточно выполнить `git commit`. Скрипт установки добавляет обработчик для объединения изменений `Info.plist`.

Git-хуки локальны: в новой копии их нужно установить отдельно. Коммиты через GitHub, `git commit --no-verify`, некоторые операции переноса истории и сторонние инструменты могут обходить локальный хук. Глобальная уникальность номеров между независимыми клонами без общего сервиса не гарантируется. Релизы публикуются отдельно после проверок.
